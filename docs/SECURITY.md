# Security boundaries — Zentro - POS v0.2.0

This is a targeted source/integration review, not an independent audit or a claim of zero vulnerabilities. Date: 1 November 2026. See `QA_REPORT.md` and the raw command outputs for executed verification.

## Controls implemented

- The live app reads/writes through an authenticated same-origin HTTP API. Client role/price/cost/company fields do not grant authority. Server session users choose company identity; caller-supplied foreign product/customer/staff/device IDs are scoped or rejected.
- Platform Power credentials can manage company/license metadata but do not have a business workspace/report endpoint. Each company has a separate SQLite file. The physical server operator and server process can access all company files; there is no cryptographic separation from that operator or PostgreSQL row-level security.
- Passwords use native Argon2id with random salt, 19 MiB memory, two passes and parallelism one. Passwords are 14–128 characters. No default accounts/passwords ship. A local interactive CLI bootstraps the first Power account; no public HTTP bootstrap exists.
- Admin and Power must enroll/verify TOTP MFA. MFA seeds use AES-256-GCM with a locally generated server key. TOTP has replay-counter protection and a one-step clock window. Recovery codes are stored as SHA-256 digests of random secrets and are consumed once. Staff MFA is not offered as a self-service feature in this version.
- Random 256-bit session tokens are stored as digests. Cookies are HttpOnly and SameSite=Strict; production additionally sets Secure. Password/MFA transitions rotate the session. Pre-auth sessions expire after 15 minutes; authenticated sessions after eight hours with 30-minute idle timeout. Logout, disabling users and access changes revoke sessions. Admin/Power role checks re-evaluate MFA requirement on every request.
- Mutations require matching Origin, session-bound CSRF header, JSON content type and body limit. Host must match the configured origin. No permissive CORS is provided. No X-Forwarded-Host is trusted. Optional forwarded client IP handling is limited to loopback proxy peers, for rate limiting only.
- Global API request limits, identifier/IP login throttling, MFA/invite throttling and four concurrent hash slots limit some brute force/resource abuse. Limits are in memory and reset on restart; public hosting needs appropriate edge controls. Request/header timeouts, header limits and a 256 KiB JSON limit are applied.
- Activation and invitation secrets are stored as digests. A separate owner invitation and valid activation key are required together to set up the first owner. Invitations expire in 24 hours and cannot be reused. Key replacement revokes old activation keys. Expiry/revocation stops business writes; records remain readable. Suspension revokes company sessions. It does not delete business data.
- Terminals use a distinct random HttpOnly registration cookie. Limits are checked transactionally; releasing a terminal invalidates its device-bound sessions and blocks new checkout through that token. Device enrollment is profile registration, not hardware attestation; OS-profile cloning or a stolen device cookie cannot be ruled out.
- Business writes use SQLite BEGIN IMMEDIATE transactions. Idempotency binds a persisted key to actor, action and payload hash. Same-key changed-payload requests are rejected. Checkout trusts current stored prices/stock and updates sale, stock, customer balance, operation result and audit together. Replayed results re-check the current branch and redact costs against the current role.
- Cashiers cannot invoke inventory/team/report/Power operations or read returned cost/profit fields. Free/discount injection is rejected for cashiers. Server-generated offers can add bonus lines after permission checks.
- Financial items are archived/disabled rather than erased. Tenant audit SQL tables reject update/delete through triggers; normal commands append events. The UI shows a recent subset. A privileged filesystem/DB operator could remove triggers or alter files; this is not an externally anchored tamper-evident audit chain.
- The HTTP static allowlist contains only UI assets. Environment files, database files, source/config/docs and arbitrary paths are not served. CSP limits scripts/styles/connect to same origin, blocks framing/plugins/inline code, and permits no third-party CDN. UI encodes user-controlled display text. SQL values use prepared parameters. CSV values are protected from formula-leading text.
- Backup archives encrypt the full snapshot, including the server MFA key, with AES-GCM and a passphrase-derived Argon2id key (64 MiB, three passes). Restore authenticates before writing, whitelists filenames and refuses nonempty destinations. The scheduler is opt-in; a single live store blocks mutations while taking database snapshots. Offsite copy, restore drills, capacity monitoring and retention remain operator tasks.
- Electron source enables sandbox, context isolation, no Node integration in the renderer, denied permissions/webviews/new windows and constrained same-origin navigation. Only the fixed developer mailto is opened externally. Local bootstrap IPC is restricted to that window/main frame/origin and cannot create a second Power account. Electron runtime behavior was not executed here.

## Residual risks and unverified areas

This server uses synchronous SQLite and a full JSON business document per tenant, with in-memory reports. It needs measured load limits and a normalized storage design for larger deployment. SQLite/Argon2 runtime APIs must be validated for every supported Node/Electron upgrade. There is no independent penetration test, desktop dependency-tree/CVE scan, fuzzing campaign, load test, Windows binary execution, signed artifact verification or physical scanner/printer test in this delivery.

A compromised server/OS can read business data, sessions and the adjacent MFA encryption key. Use restricted OS access, protected disk encryption, hardened service deployment, current runtime/security updates and off-machine encrypted backups. The application itself does not encrypt live SQLite files at rest. Do not serve the source tree with a general static web server or expose a local standalone listener to a public network.

There is no cloud offline queue, signed offline licensing/lease, hardware-bound activation, automatic updater, distributed rate-limit store, automated email recovery, email delivery, end-user password change screen, online payment gateway or certified tax/fiscal service. An operator can reset a password (MFA retained) or use a more explicit physical-operator recovery mode to reset MFA and force re-enrollment. Protect operator access; recovery is intentionally not a public unauthenticated web endpoint.

All shared-server companies rely on that one server's availability. Cloud mode stops checkout when disconnected. Local standalone data is separate and does not sync back. Do not make availability, accounting certification or offline guarantees beyond these implemented behaviors.

## Before public production use

Complete `RELEASE_GATES.md`, including an independent review against real deployment settings and a resolved desktop dependency tree. Passing automated regression checks establishes the exercised cases, not an absence of every vulnerability. Do not label this build hack-proof.
